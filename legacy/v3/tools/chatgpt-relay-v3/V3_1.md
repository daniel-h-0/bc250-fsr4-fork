# BC-250 Relay v3.1

Relay v3.1 keeps protocol `BC250_RELAY_V3` and adds three logical sessions:

- `fsr4` — FSR4 Main
- `ps5` — BC-250 Emulation Update
- `vcn` — VCN

## Job transport

Read `relay-v3/status/hello.json` for the current token and relay capabilities.

New jobs should include a `session` field and use a namespaced filename:

`relay-v3/jobs/<session>--<job_id>.json`

Example:

```json
{
  "protocol": "BC250_RELAY_V3",
  "token": "<token from hello.json>",
  "session": "ps5",
  "job_id": "inspect-sharpemu-001",
  "op": "git_status",
  "cwd": "/home/david/sharpemu"
}
```

Read the exact result from:

`relay-v3/results/<session>--<job_id>.json`

Legacy flat v3 jobs remain compatible during migration and also receive their old flat result path.

## Concurrency

FSR4, PS5 and VCN can each have one active job at the same time. A long job no longer blocks the GitHub polling/heartbeat loop or the other sessions.

## Human control

Every session has a control state with `running`, `paused`, or `stopped` mode, a priority string and recent messages. Every job result contains the latest control snapshot for its session.

Dashboard actions:

- `PAUSE` — block new jobs for that session without killing the current job.
- `RESUME` — allow new jobs again.
- `STOP` — stop the session and terminate its active shell job/process group.
- `NOTE` — add a human instruction/observation.
- `PRIORITY` — set the current human priority.

Chats should inspect the `control` object in every result and adapt to new notes/priorities rather than ignoring them.

GitHub-side control messages may also be created under `relay-v3/control/` with the relay token, session, action and optional text. Acknowledgements appear under `relay-v3/control-results/`.

## Dashboard

The local dashboard is served on port 8765 and requires the separate `dashboard_key` stored in `~/.config/bc250-relay-v3/config.json`.

The upgrade script prints the complete local dashboard URL.

## Health and watchdog

`GET /health` reports session state, active jobs and GitHub transport freshness. A user-systemd watchdog checks it every minute and restarts the relay if health/transport becomes stale.
